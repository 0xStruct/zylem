Verifiable Zcash data, no node required

Everything on this page is a plain file from this page's host: two Rings of 4,096 blocks and two history proofs made on a GPU. Your browser checks all of it with the same Rust code a Zylem client runs, compiled to WebAssembly. The host is not trusted for any of it.

Open a Ring

A Ring holds 4,096 consecutive blocks: every full header, every transaction in the compact form wallets already download, a few hundred bytes of digests per transaction so its ID can be rebuilt, and the tree state it starts from.

These IDs were rebuilt here from the compact data and digests in the Ring, and together they produce this header's Merkle root. A server that changed any transaction could not make them match.

2

Check the whole Ring

The full client check, block by block. This is what lets any mirror, CDN or stranger host Rings: a client accepts nothing it cannot rebuild.

  • Every header has a valid Equihash solution, meets its own target and links to the one before; the difficulty and time rules apply once 113 earlier headers are known.
  • Every transaction ID is rebuilt from the compact data and digests, and the IDs reproduce each header's Merkle root.
  • The history tree, replayed block by block, matches what every following header commits to, which authenticates each block's tree roots.
  • The Ring's note commitments, appended to its starting tree state, reproduce those authenticated roots, so every tree state inside is authenticated too.
3

Find a payment

Look up a transaction by its ID among the IDs rebuilt in step 2. A server can only make a payment appear if the Ring's own data rebuilds that exact ID inside an authenticated block.

4

Try to lie

Each button makes a copy of the open Ring altered the way a dishonest server would, then runs the step 2 check on it. The server would also publish a matching file hash, so only verification can catch it. The target follows the block opened in step 1; any transaction works.

Invent an incoming note

Adds a fake Ironwood action, as if someone had paid the wallet.

Hide a payment

Leaves one transaction out of its block, so the wallet never sees it.

Serve a wrong tree state

Swaps the starting Ironwood tree for another of the same size, so a wallet would build unspendable anchors.

5

Verify succinct proof on mobile and on-chain

A succinct proof of Zcash data stays small and quick to check however many blocks it covers. One SP1 proof states that every header in a range passed Equihash, its target and the difficulty rules, and commits to a 104-byte record of each block. The same claim comes in two forms: one a phone checks, and one a smart contract checks.

On mobile

1.27 MB

A compressed STARK, with no trusted setup. It verifies in this browser in a few dozen ms on whatever device opened this page, then stands in for every header it covers.

On-chain

356 bytes

The same claim wrapped in Groth16 over BN254, the form SP1's verifier contracts check on EVM chains. It verifies here in a few hundred ms. No contract is deployed yet.

Light wallet vs Zylem

Don't trust, verify

Today's Zcash light wallets download compact blocks from a light-wallet server and take them as given. Zylem gives the same wallets data they can check. Steps 2 to 5 above are the checks in the Zylem columns, run on this page.
